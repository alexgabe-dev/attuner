# Server recovery boundary

Phase 4 implementation decision: maintenance is an explicit operator CLI, not an HTTP/Tauri filesystem endpoint. Stop the service before a drill. A SQLite IMMEDIATE writer lock additionally prevents accidental concurrent publication/administration during capture. A second read-only connection uses SQLite's backup API while the writer lock is held; copying a live SQLite file/WAL with ordinary file copy is forbidden.

Copy only database-referenced immutable verified CAS objects and receipted upload chunks. Unpublished temporary/orphan files are not synchronization authority and remain untouched in the source. There is no garbage collection. The database and reference inventory share the same locked capture point. Capture/complete/failure/restore events use the existing append-only audit tables, and audit failure prevents sealing/activation.

Backups are new private directories containing separately AES-256-GCM authenticated encrypted files, an encrypted bounded-line catalog, and a final create-new completion receipt. Bind every ciphertext to its backup UUID and logical entry with AEAD associated data. A backup key is independent of TLS/device/token-delivery keys and is never placed in arguments, logs, repository files or the backup. Production delivery uses an operator secret manager/inherited descriptor; tests use random in-memory keys. A partial directory without a valid authenticated catalog/receipt is never a restorable backup.

SQLite's backup API requires a filename. Its temporary plaintext capture stays inside the already private server data directory, never in the external backup destination; staging requires an encrypted server data volume. Interrupted scratch material is retained for operator inspection rather than silently removed/adopted. Normal completion removes only the maintenance operation's own scratch snapshot after encryption. Explicit restore necessarily creates plaintext database/configuration bytes in a new private, encrypted-at-rest service data volume.

Restore verifies encryption, bounded sizes/entry names, SQLite integrity/foreign keys/exact known schema, immutable manifest digests/seals/parent revisions/profile heads, referenced content hashes and the original audit cutoff/digest. The output root is created exclusively and remains marked unavailable until all checks and a durable restore audit succeed. Existing roots are never overwritten. Preserve the original server UUID and observed revision history; clients still enforce identity/high-water marks and refuse older restored heads.

**Revocation rollback policy:** restoring an older database could otherwise resurrect devices, sessions, pending enrollment grants or account passwords revoked since capture. Without an independently durable external revocation ledger, restore must fail closed: atomically revoke all captured devices/credentials, increment web-session epochs, disable all accounts and deny pending/approved enrollments, with a restore audit event in the same transaction. The operator must explicitly recover one administrator using the hidden-input local CLI, then review other accounts and explicitly enroll new device keys. No old credential is silently re-enabled; encrypted backups are not a revocation authority. This is separate from ordinary signed-upgrade credential persistence. Tests must prove old access fails and new approved enrollment reconnects without discarding local snapshots or revision high-water marks.

The backup is a point-in-time image: its audit history includes capture intent, while sealing is recorded on the live source and in the final external receipt. A restore appends its own event after verifying the captured audit history; it does not invent completion events inside old history. TLS material requires separately managed encrypted secret recovery or replacement under the existing trusted CA. Rotate the token-delivery key after restoration; revoked devices and denied pending enrollments cannot redeem old deliveries, and new approved enrollments use the replacement key. Neither secret is silently bundled into a data backup.

All automated drills use newly minted synthetic directories. Process interruption evidence, clean restore, native client reconnection and staging operations must be reported separately; no VPS deployment or power-loss claim is implied.
