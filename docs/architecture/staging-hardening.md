# Non-production staging boundary

## Jammy / shared-host adaptation (approved target, not deployment)

The supplied host inventory supersedes the original dedicated Ubuntu 24.04 assumption: Ubuntu 22.04.5 x86-64, 11 GiB RAM, 4 GiB swap, 288 GB available root storage; CPU count, filesystem/encryption policy, installed Nginx version and the dedicated HTTPS hostname remain unverified. `pry.hu` is an inventory hostname, not an approved Attuner origin. No host connection is authorized.

The renderer now targets systemd 249 and an **HTTP-context include in the existing Nginx**, without changing its master configuration, worker count, default server, listeners, certificate automation or other sites. No standalone proxy service is installed by this profile. Only the new explicit hostname routes to configurable loopback ports. Named zones/variables and server-local limits/logging/cache are Attuner-specific. The host's existing approved TLS certificate/key management remains a prerequisite; the bundle does not acquire keys or make shared Nginx depend on an Attuner-only runtime unlock.

Jammy has `LoadCredential`, but not `LoadCredentialEncrypted`. Authenticated age-encrypted files remain on disk; an explicit root operator helper decrypts bounded fixed credential IDs into a root-private tmpfs directory, then systemd copies them into its existing private read-only credential facility. The helper never receives a password through arguments/environment, publishes no credential until authentication succeeds, never replaces existing output and creates a role-ready receipt only after every credential succeeds. No automatic unlock or persistent plaintext fallback. Reboot leaves Attuner locked until an operator unlocks it; unrelated Nginx sites must continue to start normally. Swap/volume encryption and existing public TLS-key handling must be reviewed before real secret provisioning.

API, dashboard and monitor retain distinct non-root identities; a shared Attuner-only slice caps aggregate CPU, RAM, swap and tasks. Read-only versioned releases, private data/backups/configuration and scoped log retention keep application writes away from other sites. At least 10 GiB free-space reserve is proposed for this shared disk, not a disk reservation. No cgroup, Nginx, swap, firewall or service changes are performed by local rendering/tests. Deployment, decrypted secret delivery and operator rollback remain separately approved host steps.

Primary compatibility evidence: [systemd 249 credentials](https://github.com/systemd/systemd/blob/v249/man/systemd.exec.xml), [Jammy systemd package](https://packages.ubuntu.com/jammy-updates/systemd), [Jammy age package](https://packages.ubuntu.com/jammy/age), [Node 24 Linux ABI](https://github.com/nodejs/node/blob/v24.22.2/BUILDING.md), [Nginx name-based virtual hosts](https://nginx.org/en/docs/http/server_names.html). The older dedicated-gateway design below is retained as historical qualification context, not the generated Jammy deployment profile.

The prepared target is one Linux VPS with a single HTTPS origin, Fastify/SQLite/CAS and Next.js, preserving the approved architecture. No peer-to-peer path or new backend filesystem authority is introduced. **Nothing is deployed or enabled by the renderer/tests.**

The historical dedicated-host profile used systemd 255+ services with `LoadCredentialEncrypted`, rather than the development-only Compose file. This supplies authenticated encrypted-at-rest secrets through per-service private runtime credentials and avoids persistent plaintext `.env`/Docker secret bind files. It is an operational packaging choice, not a change to protocol or storage architecture. No existing host settings, Keychain ACLs or service permissions have been changed.

Four isolated service users separate API/data, web, HTTPS gateway and readiness monitoring. Only the gateway receives bind-to-443 capability. Code/configuration are read-only; API writes are limited to its private data volume. The dashboard and gateway cannot read database/blob/backup secrets. The manual backup service conflicts with/stops the API and receives only its dedicated backup key. Monitor timers are supplied but never enabled by these tools. There is no automatic backup, synchronization, retention or GC policy.

Browser/desktop → gateway and gateway → API use verified TLS. Next.js binds HTTP only on loopback behind the gateway; it receives no synchronization/signing secrets. API binds HTTPS on loopback. The public origin is fixed and must match CSRF/DPoP proofs; the gateway preserves Origin/authorization/cookies/proofs while overwriting forwarded client-address headers. Fastify trusts forwarded addresses only from loopback when explicitly configured; authentication never trusts a forwarded origin. Unknown upstream CA/name, missing runtime credentials, low reserve or incomplete restore fails closed.

The gateway streams request/response bodies without temporary-body caching, bounds sizes/time/connections/login rate, and logs only a generated ID, allowlisted method, broad route class, status and duration. Raw Nginx error logs are disabled because they may include request URIs; failed requests remain visible in sanitized status logs and process/service status. Fastify disables default request/error serialization and emits an allowlist of metadata, omitting headers, bodies, actual parameters, queries, errors and host names. Security audit trails remain transactional SQLite records; operational request logs are not their replacement. No telemetry is sent externally.

Storage enforces existing per-profile quota/transfer limits plus a configurable physical free-space reserve (minimum 16 MiB; historical staging 512 MiB; shared Jammy profile 10 GiB). Readiness checks real database and object-store availability/reserve. A separate credential-free local HTTPS monitor returns a nonzero status on outage/low readiness; a bounded backup-receipt monitor reports stale/incomplete/corrupt latest catalog metadata without a decryption key. Receipt freshness is not proof of backup decryptability; actual encrypted restore drills remain required.

Validation uses freshly minted synthetic roots, encrypted PKCS#8 fixture keys and a private FIFO to deliver the test gateway passphrase only through kernel memory. No global trust store or persistent plaintext secret file is used. The local Mac's pre-existing Nginx and a digest-pinned official Linux Nginx image qualify actual proxy behavior independently; systemd directive validation/activation and encrypted-credential provisioning must be reported separately. An undeployed configuration is not a qualified VPS.

References: [systemd credentials](https://systemd.io/CREDENTIALS/), [systemd 255 credential loading](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html#LoadCredential=), [Nginx verified upstream TLS](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_ssl_verify), [Nginx password FIFO](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_password_file). Version/security selection uses the vendor's [downloads](https://nginx.org/en/download.html) and [advisories](https://nginx.org/en/security_advisories.html): stable 1.30.6, with the official validation image pinned by OCI digest in `toolchain.json`.
